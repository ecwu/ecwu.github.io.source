# DGX Spark 固定部署测试脚本审阅

审阅日期：2026-09-29。对象：用户提供的代码包，解包到 `/tmp/dgx-fixed-review/dgx-fixed-deployment-test`。

结论：组织结构符合修订方案，但正式测试前需要修正以下问题。此次只做静态检查和离线模拟，没有调用远端服务、启动模型或运行性能测试，也没有修改待审脚本。

## 1. P1：实际生效配置没有得到核验

位置：`scripts/run-suite.py:109–141`、`275–285`。

`verify_launch_evidence()` 只在已有 dry-run 文本中搜索参数。启动后的检查只确认模型名和一个整数上下文上限，未把实际进程、实际生效配置与本次运行段绑定。旧 dry-run 符合意图，而运行实例的 MTP、KV、调度或缓存设置不同时，仍会开始测试，并给结果写入 YAML 的配置标识。

修正：从当前服务的进程参数、容器环境和本次启动日志提取生效配置；记录本次实例身份及启动时间，并逐项匹配冻结配置。测试期间核对实例是否发生替换。dry-run 仅作为部署意图保存。配置为 false 的开关也需要核对，而不是只检查 true 的开关。

验收：准备符合意图的 dry-run、但不同的运行实例，必须在正式请求前拒绝运行。

## 2. P1：B 组请求没有整体超时

位置：`scripts/benchmark.py:58–60`、`433–442`。

HTTP 客户端关闭了读取超时。A/C 经 `round()` 套用整体超时，B 则直接 await `one_request()`，没有使用测试配置中的 1800 秒预算。后端接受请求后不继续返回，B 会一直等待，超时终止运行段及恢复服务的逻辑无法自动执行。

修正：在统一请求入口落实整体 deadline，并让 B 首次请求发生超时/OOM/后端断连时立即结束运行段，不再提交重复请求。tokenize 等辅助调用也需要有界等待。超时记录保留已观测数据，但完成时延和 TPS 不进入正常统计。

验收：用接受连接后保持沉默的模拟服务，B 在缩短的测试 deadline 内记录 timeout，结束运行段，并进入恢复流程。

## 3. P1：续跑和汇总没有隔离配置与协议

位置：`scripts/benchmark.py:350–365`、`420–425`、`465–474`；`scripts/validate-results.py:21–29`、`71–74`、`94–100`、`164–168`。

断点续跑根据 cell、pair、segment 和 included 判断已完成，没有匹配配置标识、测试设置或已验证的生效配置。汇总也读取当前代码目录里的 YAML。配置发生改变后，旧请求可能被跳过，并被归到当前配置之下；结果目录里的配置和环境文件还会被续跑覆盖。

离线复现：给 A 组传入旧配置的三个有效轮次，当前配置的 `build_a()` 仍返回 `ok`，并汇总旧请求。

修正：按运行段保存不可覆盖的生效配置、测试设置和协议版本；续跑前逐项比较，只有相同部署和协议才可跳过或合并。离线工具读取结果包内的冻结配置。配置改变时创建独立结果目录或独立部署条目。

验收：修改 MTP、输出预算或并发设置后，旧数据不能填入新配置矩阵，也不能被标记为已完成。

## 4. P2：A 组会汇总失败轮中的成功请求

位置：`scripts/validate-results.py:21–30`、`43–62`。

没有完整三轮时，选择函数会返回某运行段的全部轮记录。后续请求筛选只检查轮次编号和请求 included，没有要求所属轮 valid。因此一轮中其他请求失败，该轮的成功请求仍会进入 TTFT、decode TPS 和端到端时延。

离线复现：只有一个失败轮和一个成功请求时，矩阵显示 `valid_rounds=0`，同时 TTFT 中位数为 1 秒、样本数为 1。

修正：任何正常性能汇总只使用有效完整轮内的请求。不足三轮可以保留已完成轮的描述统计并明确样本数；失败轮里的成功请求只出现在原始记录和完成情况中。`valid_rounds` 应报告实际有效轮数。

验收：并发 2 的一轮里一个成功、一个失败，成功请求不能进入该格正常性能统计。

## 5. P2：C 组缺少流完成条件

位置：`scripts/benchmark.py:187–217`、`227–243`。

C 的长度校验只要求输入正确、输出计数在预算内，未要求合理的 finish_reason 或明确的流结束证据。连接正常关闭、但流中没有完成标记时，仍可能被记为成功。

离线复现：模拟服务发送正文和 usage，然后直接关闭流，没有 finish_reason 和结束标记；记录仍是 `execution_status=ok`、`transport_completed=true`、`included=true`。

修正：分别记录接收结束标记、完成原因、最终 usage 和传输结束；按核实后的接口语义判定完成。没有完成证据的输出保留为不完整观测，不能算自然 EOS 或成功预算截断。若 reasoning 被隐藏，也要有可验证依据才能描述为隐藏推理。

验收：缺少完成证据的模拟流被标为 incomplete/invalid；正常 EOS 和正常预算截断仍有效。

## 6. P2：外部干扰字段始终为 false

位置：`scripts/benchmark.py:240–243`；`scripts/telemetry.py:35–48`。

启动前的独占检查有价值，但请求记录把 external_interference 固定为 false。测试开始后出现其他请求、其他 GPU 任务或服务实例变化，都不会改变该字段。当前遥测没有把这些证据与请求/轮次关联，也没有完成请求计数供离线核对。

修正：持续记录并关联服务完成计数、队列、GPU 进程和实例身份；存在额外工作则排除对应轮或配对，缺少证据时标为 unknown。B 的配对有效条件也要同时检查两条请求的干扰状态。

验收：插入额外请求后，受到影响的轮次/配对不能继续作为无干扰样本；遥测不可用不能自动等同于 false。

## 7. P2：usage-only SSE 事件没有落盘

位置：`scripts/benchmark.py:194–216`。

usage 在内存中更新，但事件记录写在 choices 循环内。choices 为空的最终 usage 事件不会保存，结束标记也不保存。结果里的准确 token 计数因此无法从公开事件记录重新核对；这也削弱了流完成条件的离线检查。

修正：每个 SSE 数据事件只记录一次时间、事件类型、usage 和脱敏的选择状态；单独记录结束标记及异常。继续避免复制生成文本。

验收：一个 choices 为空的 usage 事件和一个结束标记，都能在事件文件中找到并用于离线重算。

## 其他交付缺口

- `validate-results.py` 大多信任 included、length_valid、round.valid 和已有指标，没有重算长度、时间公式、轮请求数和配对收益。其报告里的“checked”表述超过目前实际检查范围。应补上重算及引用关系检查。
- 服务控制器不在代码包内，无法确认 start 是否保证新实例、是否等待健康状态、是否持有协调锁，以及恢复是否还原原服务配置。需要远端提供相关实现或可审阅片段。
- 恢复检查只核对模型列表，没有通过短请求确认恢复后的正常响应。
- 环境记录缺少容器内推理框架、PyTorch/CUDA 版本和实际加载、KV 预算证据；这些仍需要随结果交付。
- 配置中的 max_tokens、temperature、timeout 等字段部分被实现里的固定常量替代。当前默认值一致，但配置修改不会全部生效，应统一来源或拒绝与固定协议不一致的设置。

## 本轮验证

全部 Python 源码通过编译检查。用标准库构造离线依赖替身和模拟流，复现了失败轮汇总、跨配置汇总、C 流完成判定三个问题；没有执行任何真实 HTTP 模型请求。当前本机 Python 缺少 httpx，因此没有进行真实依赖下的端到端测试。
